# 事故台账

> 一条事故一条记录。**必须有出口** —— 出了事故不是修完就算完，
> 要留下一个装置保证同样的问题下次会立刻被发现。
>
> 标题只认两种形态（解析器硬校验），**编号要包反引号**
> —— 裸写会被 GitLab 转成 Jira 死链：
>
> ```text
> ### `INC-NNN` · YYYY-MM-DD · 标题
> ### `INC-NNN` 补记 · 标题
> ```
>
> 每条必填五项：`- **现象**：` / `- **根因**：` / `- **出口**：` /
> `- **状态**：` / `- **同类扫描**：`。
> 状态取值只有 `已闭环` / `半闭环` / `未闭环`；
> 半闭环必须另写 `- **升级条件**：`（什么情况下要做成机制）。

## 记录

### `INC-001` · 2026-08-10 · `payment-cli` 没有 README，而没有任何东西发现过

- **现象**：装护栏时把四个 CLI 的 README 都写进 `harness/doc-targets.json`
  的受检目标，`doc-refs` 当场退 **2**：

  ```text
  [第三态] 受检目标不存在：apps/payment-cli/README.md
    这不是「没有失效引用」—— 受检范围缩小了。
  ```

  核实：`apps/payment-cli/` 下只有 `package.json` / `src` / `tests` /
  `tsup.config.ts` / `dist`，**四个 CLI 里只有它没有 README**。
- **根因**：这个仓库此前没有任何检查在看「文档齐不齐」。
  `admin-cli` / `merchant-cli` / `token-cli` 都有 README，
  `payment-cli` 少一份 —— 而**少一份文档不会让任何测试失败、任何构建报错**，
  所以它可以一直缺着。

  值得记的是发现方式：不是有人去清点，是**装一道检查的时候被它的第三态撞出来的**。
  那道检查的设计是「受检目标不存在 → 退 2，而不是静默缩小范围」，
  正好把这件事变成了一个不能忽略的信号。
- **出口**：`harness/doc-targets.json` 的 `刻意不收进来` 里记下这一条，
  并写明「补了 README 之后要回来把它挪进 `目标`」。
  也就是说这份缺失现在**有一个会被读到的位置**，不再只存在于「没人注意」里。

  更强的出口需要一道「每个 `apps/*` 都要有 README」的检查 ——
  按本仓约定，**规则要从事故长出来**，这是第一条，先记下来。
  出现第二次（比如新加的 CLI 又忘了 README）就把它做成检查。
- **状态**：半闭环
- **升级条件**：再出现一次「某个 `apps/*` 缺 README / 缺文档」，
  就在 `check_doc_refs.py` 之外加一道「每个 workspace 包必须有 README」的检查
  （或把它并进 `layout-check`）。**一次是个案，两次是形态。**
- **同类扫描**：按「某类文件在一部分目录里有、在另一部分里没有」这个形态
  扫了 `apps/` 与 `packages/` 下的其余文件：
  四个 CLI 都有 `package.json` / `src/` / `tsup.config.ts`，
  只有 `admin-cli` / `merchant-cli` / `token-cli` 有 `docs/`（`payment-cli` 没有，
  与 README 同一处缺失）；`tests/` 四个都有。
  除 README / docs 这一处外没有别的不一致。
